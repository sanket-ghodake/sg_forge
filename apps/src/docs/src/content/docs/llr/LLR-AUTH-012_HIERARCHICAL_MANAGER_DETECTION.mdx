## 1. Algorithmic Specification

1. Receive target employee identifier via route parameter (`:id`), query string (`?user_id=...` / `?email=...`), or session token (`/me`).
2. Resolve user record in `auth_users` using strictly parameterized queries to prevent SQL injection.
3. Compute direct subordinate report count `count = sum([r.related_to_id == user.id and r.is_primary == 1])` in `auth_employee_relationships`.
4. Assert boolean condition: `isManager <=> (count >= 1)`.
5. Return standardized `EmployeeManagerCheckResponse` payload with HTTP 200, or RFC 7807 problem details (401 for unauthenticated `/me`, 404 for non-existent employee).

## 2. Safety & Verification Invariants

* **Designation Independence**: Job title strings, designations, or IAM role names MUST NEVER influence manager status. Manager state is exclusively derived from direct child nodes in the reporting hierarchy.
* **Bounded Latency**: The calculation must execute as an indexed $O(1)$ count query without recursing upward management chains.
* **Authentication Boundary**: Calling `/me/is-manager` requires an active, unexpired session token or returns RFC 7807 401.
* **Zero PII Leakage**: The response returns only `status`, `userId`, `isManager`, and `directReportsCount` without leaking credentials or unrelated user metadata.
