## 1. Portal Architecture & Navigation Lifecycle

The SG Forge Portal (`@forge/portal`) strictly operates as a Single Page Application (SPA). Hard page refreshes during navigation are strictly forbidden by architectural directive 15.

## 2. Technical Specifications

### Client-Side View Dispatcher
* **History State Integration**: Navigation clicks intercept standard anchor events, pushing route states via `history.pushState(null, '', path)` and dispatching internal view hydration events.
* **Instantaneous View Transitions**: Views are rendered client-side using lightweight DOM templates without round-trip HTML page reloads.
* **Responsive Layout Engine**: Viewports adjust dynamically across Desktop (>1200px), Tablet (768px - 1199px), and Mobile (320px - 767px) with zero horizontal scrollbars.

### Iframe Sandboxing & Security Boundaries
When rendering autonomous Forge submodules inside the Portal:
* Micro-apps are loaded inside isolated `<iframe>` elements configured with strict sandbox attributes:
  ```html
  <iframe 
    src="/apps/code/" 
    sandbox="allow-scripts allow-same-origin allow-forms"
    referrerpolicy="strict-origin-when-cross-origin"
    class="forge-submodule-frame">
  </iframe>
  ```
* **PostMessage RPC Bridge**: Cross-origin communication between the Portal shell and embedded Forge apps uses cryptographically validated JSON payloads:
  ```typescript
  window.addEventListener('message', (event) => {
    if (event.origin !== expectedOrigin) return;
    handleSubmoduleEvent(event.data);
  });
  ```
