## 1. Authentication & Session Lifecycle Overview

The SG Forge Authentication Engine operates inside the core air-gap zone (`core-airgap-net`). It issues cryptographically signed JWT cookies with strict `HttpOnly`, `SameSite=Lax`, and `Secure` attributes.

## 2. Invariants & Security Specifications

### Invariant 1: Sliding Window & Inactivity Timeout
* Sessions have an active sliding expiration (default 30 minutes of idle inactivity).
* Every authenticated request automatically renews the session timestamp in the session store.
* Once the idle limit is exceeded, subsequent requests return an RFC 7807 `401 Unauthorized` with `urn:sgforge:error:session-expired`.

### Invariant 2: Anti-Replay Token Defense
* Session tokens include unique cryptographic `jti` (JWT ID) identifiers and sequence counters.
* The Auth Engine maintains an in-memory or SQLite-backed token revocation blacklist. If a previously refreshed token is presented again, both the replayed token and the current active session are immediately revoked to protect against man-in-the-middle interception.

### Invariant 3: Zero Credential Exposure
* All authentication cookies are marked `HttpOnly`, preventing client-side JavaScript from accessing session tokens.
* Cross-Site Request Forgery (CSRF) is neutralized through strict origin verification and SameSite cookie policies.

### Invariant 4: Return URL State Preservation on Inactivity Logout
* When a session expires (via inactivity timeout or 401 response detection), the current page URL is captured and encoded as `?return_url=<encoded-path>` in the auth login redirect.
* On successful re-authentication, the user is automatically returned to the exact application and view they were working in — zero work state loss after an inactivity timeout.
* The `forge_return_url` key in `sessionStorage` is consumed and removed after a single use to prevent stale replays on subsequent login sessions.
* The multi-step first-time password setup flow also threads `return_url` through all intermediate pages, ensuring continuity even for onboarding users.

### Invariant 5: Real-Time Cross-Tab Logout Synchronization
* Logout events initiated in any browser tab (Portal sign-out button or automatic HTTP 401 detection) are instantly broadcast to all other open tabs via two parallel channels:
  - **`BroadcastChannel('forge_auth_channel')`**: delivers a `{ type: 'LOGOUT' }` message to all same-origin tabs within milliseconds, without requiring a page refresh.
  - **`localStorage` key `forge_logout_event`**: serves as a universal cross-browser fallback via the `storage` event, which fires in all other tabs that did not write the value.
* All Portal tabs **and** all open Forge App tabs (open in separate browser tabs) receive the signal simultaneously and redirect to the login page, each preserving their own current URL via `?return_url`.
* A `fetch()` interceptor installed at boot time in every app automatically detects HTTP 401 responses and emits the cross-tab logout signal — Forge Apps running in separate tabs are never left in a stale authenticated state even without manual refresh.
