## 1. Submodule Governance & Isolation Model

Forge Apps reside in `forge-apps/*` as autonomous Git submodules. They possess complete independence from core platform internal libraries.

## 2. Invariants & Autonomous Rules

### Invariant 1: Zero Imports from Core (`apps/src/*`)
* Forge submodules MUST NEVER import code from `apps/src/*`.
* Shared platform functionality is consumed exclusively through published, versioned packages (`@forge/sdk`, `@forge/ui`, `@forge/types`).

### Invariant 2: Independent Container Lifecycle
* Each Forge App maintains its own standalone `Dockerfile` and `.dockerignore`.
* Micro-apps operate on `forge-apps-net` with their own environment variables, local port mappings, and health checks.

### Invariant 3: Independent AI Agent Governance
* Each submodule maintains its own local `AGENTS.md` and `GEMINI.md` with localized instructions and domain invariants.
* Changes to submodule applications do not invalidate or require rebuilding core platform containers.

## 3. Submodule Environment & Auth Architecture

### Asymmetric Token Trust & Ingress Boundaries
Central authentication (`apps/src/auth`) signs session tokens. Forge micro-apps sit behind Caddy on `forge-apps-net`, parsing session claims from cookies without storing symmetric signing secrets (`JWT_SECRET`). This strictly eliminates secret sprawl across submodule repositories.

### Standalone vs Gateway Redirection (`AUTH_SERVICE_URL`)
When running behind Caddy, `AUTH_SERVICE_URL` is empty, defaulting to relative `/auth/login`. When running standalone without the gateway, developers specify `AUTH_SERVICE_URL=http://localhost:3000` to redirect unauthorized users to the host auth service.

### Canonical Submodule Environment Variables
| Variable | Required | Default | Description |
| :--- | :--- | :--- | :--- |
| `PORT` | Yes | `3010` | Micro-app HTTP service port |
| `NODE_ENV` | Yes | `development` | Node runtime environment mode |
| `CONTAINER_PREFIX` | Yes | `forge-app-template` | Docker container prefix name |
| `APP_NAME` | Yes | `app-template` | Microservice identifier |
| `AUTH_SERVICE_URL` | No | `""` | Standalone auth redirect URL (empty behind gateway) |
| `DATA_DIR` | No | `./data` | Local Turso SQLite data path |
| `LOG_DIR` | No | `./logs` | Structured JSON logs directory |
| `SESSION_COOKIE_NAME` | No | `forge_session` | Session cookie identifier |
| `BRAND_NAME` | No | `SG Forge` | Display platform name in Astryx UI |
| `BRAND_DOMAIN` | No | `sgforge.local` | Platform host domain |

## 4. Developer Workflow & Submodule Operations

### Cloning with Submodules
```bash
# Clone repository including all autonomous micro-apps
rtk git clone --recurse-submodules <repo-url>

# Or inside an existing workspace:
rtk git submodule update --init --recursive
```

### Developing Inside a Forge App Submodule
```bash
# Navigate to submodule
cd forge-apps/app-template

# Run local development with instant watch mode
rtk ./run.sh dev

# Execute local isolated 5-tier test suite
rtk ./run.sh test

# Verify submodule pre-commit gates
rtk ./run.sh verify
```

### Standalone Docker Execution
```bash
# Launch submodule in isolation (auto-bootstraps network if missing)
cd forge-apps/app-template
./run.sh up
# Or standard docker compose:
docker compose up -d --build
```

## 5. Dynamic Network Configuration (`FORGE_APPS_NETWORK`)

The Docker mesh connecting the gateway to micro-apps is dynamically configured at runtime via the `FORGE_APPS_NETWORK` environment variable.

* **Default Value**: `ag_forge_apps_net` (or `${CONTAINER_PREFIX:-ag}_forge_apps_net`).
* **Runtime Override**: Define `FORGE_APPS_NETWORK="my_custom_mesh"` in `.env`.
* **Universal Binding**: Both core compose files (`docker/dev`, `docker/prod`) and submodule compose files (`forge-apps/*/docker-compose.yml`) bind to this same runtime variable, preventing network naming discrepancies.
* **Auto-Bootstrapping**: Submodule `run.sh` scripts check for this network and auto-create it if it does not yet exist, guaranteeing standalone execution on fresh machines.

## 6. Diverse Ingress Mapping (Beyond Local Containers)

Forge Apps are not restricted to local Docker containers on the same host. The declarative registry in `.env` supports multiple network deployment topologies:

```env
APP_<ID>="<Display Name>|<Port>|<Ingress Path>|<Category>|<Access Role>|[Upstream Target Override]"
```

### Topology 1: Standard Submodule Container
Runs on the shared Docker bridge network (`forge-apps-net`):
```env
APP_TELEMETRY="Live Telemetry|8087|/apps/telemetry|Operations|Public|app-telemetry"
```

### Topology 2: Host Machine Native Process (Bare-Metal)
Runs directly on the host machine OS (e.g. Bun, Node, Go, or Python) on port `5000`:
```env
APP_TOOL="Native Dev Tool|5000|/apps/tool|Developer|Developer|host.docker.internal"
```
*Caddy reaches the host process via `host.docker.internal:host-gateway`.*

### Topology 3: Remote Cloud / Intranet Microservice
Runs on an external server, VM, or Kubernetes cluster:
```env
APP_CRM="Enterprise CRM|443|/apps/crm|Sales|Employee|https://crm.corp.internal"
```
*Caddy terminates TLS, proxies to the remote HTTPS endpoint, and forwards identity headers.*

### Topology 4: Multi-Machine Cluster (Core on Server A, Apps on Server B)
Core platform runs on `192.168.1.10`, Forge App runs on `192.168.1.50`:
```env
APP_TELEMETRY="Telemetry App|8087|/apps/telemetry|Operations|Public|http://192.168.1.50:8087"
```

## 7. Reverse Proxy Subpath Asset Routing & Image Protection Rules

When micro-apps are exposed under a subpath (e.g. `/apps/telemetry/`), asset routing must follow strict reverse proxy standards:

### Invariant 1: Canonical Trailing Slash Redirection
* Requests to `/apps/telemetry` are automatically redirected via `308 Permanent Redirect` to `/apps/telemetry/`.
* **Why**: Without a trailing slash, browsers interpret `/apps/telemetry` as a file at `/apps/` and resolve relative assets (`<img src="logo.png">`) to `http://domain/logo.png` (domain root = 404).

### Invariant 2: Relative Asset Paths or Base Href
* Micro-apps must NEVER hardcode leading-slash asset paths (`<img src="/logo.png">`) or leading-slash API fetches (`fetch('/health')`).
* Use either:
  1. HTML `<base href="/apps/<app-id>/">` in the document `<head>`.
  2. Relative paths: `<img src="./logo.png">` or `fetch('health')`.
  3. Framework base paths (e.g., Next.js `basePath: '/apps/<app-id>'`, Vite `base: './'`).

### Invariant 3: Content Security Policy (CSP) Image Governance
* Platform CSP enforces `img-src 'self' data: blob:`.
* In-memory canvas rendering, file previews, and SVG blobs are fully permitted offline.
* If an autonomous app requires external CDN images (e.g. avatars), configure a scoped CSP override in Caddy (e.g. `@codeApp` pattern in `scripts/generate-proxy.ts`).
